## 1. Engine & project setup

- Godot 4.x (developed on 4.7 stable, build 5b4e0cb0f). Binary at `~/tools/godot` (symlinked to `/usr/bin/godot` for tooling).
- Viewport: 720×1280 portrait, stretch mode `canvas_items`, aspect `expand`.
- Rendering: Forward Mobile (Vulkan) on desktop; mobile targets expected.
- **Autoload order** (project.godot, fixed — later entries may depend on earlier ones):
  `Paths → EventBus → SaveSystem → SettingsManager → LocalizationManager → Analytics → RemoteConfig → IdentityService → SocialManager → OnlineService → AudioManager → AdManager → GameplayRegistry → StageCatalog → ScreenManager → UIManager → DevTools` (OnlineService per §3.18 — after SocialManager because it wires the real backends onto it; GameplayRegistry/StageCatalog per §3.14).
- Autoload `_ready()` runs BEFORE the main scene: nothing may persist to save before `SaveSystem.load_save()`.
- Main scene: `scenes/main.tscn` + `scripts/main.gd` (boot order in §3.1).

## 2. Architecture rules

1. **EventBus is the ONLY cross-system channel.** Managers emit; any node may listen. No manager calls another manager's methods directly (UI screens talk to managers via their public APIs — that is data access, not system-to-system signaling).
2. **Autoloads have NO `class_name`** (they are global singletons); all other primary scripts DO (`class_name` for global type access; no `load()`/`preload()` of scripts where a class name suffices).
3. **Static typing is mandatory** on all declarations (AGENTS.md). Warnings are treated as errors — the import gate fails on any new warning.
4. **Code-first UI**: minimal .tscn; UI is built in GDScript. All colors/margins from `ThemeFactory` (no hardcoded values).
5. **Screens are cached and reused, never freed** (ScreenManager holds one instance per id); all `_ready()` work must be idempotent (guarded flags) and `_exit_tree()` must disconnect everything.
6. **Mock content sits behind production-shaped seams** (§"Service swap seams") — swapping a mock for a real service must not touch UI or flow code.

## 3. Module contracts

### 3.1 Boot order (scripts/main.gd)

### 3.3 SaveSystem (core/save_system.gd)
- File: `user://save.json` (`Paths.SAVE_PATH`). Shape: `{"version": <int>, "domains": {<domain>: {...}}}`.
- **SAVE_VERSION = 1**. Atomic write: serialize to `<path>.tmp`, POSIX-rename over the real file. Corrupt/unparseable saves are quarantined to `<save>.corrupt_<stamp>` and a fresh save starts (`save_failed` emitted). Saves NEWER than supported are also quarantined (no downgrade).
- **Migrations**: `register_migration(from_version, to_version, Callable(domains: Dictionary) -> Dictionary)`; run in order on load when `disk_version < SAVE_VERSION`; a missing migration path is an error. Register defaults in `_register_default_migrations()`.
- Guards: `save_game()`/`clear_save()` are no-ops with a warning if called before `load_save()` while a file exists (boot-order protection).
- Signals: `save_loaded(version)`, `save_saved(version)`, `save_failed(error_string)`, `save_cleared`.
- API: `get_domain(d) -> Dictionary` (deep copy), `set_domain(d, payload)`, `get_value(d, k, default)`, `set_value(d, k, v)`, `has_saved_game()`, `clear_save()`.

### 3.5 SettingsManager
- Owns the `settings` domain exclusively. Per-flag signals: `music_volume_changed`, `sfx_volume_changed`, `language_changed`, `haptics_changed`, `music_enabled_changed`, `sfx_enabled_changed`, `notifications_changed`, `reduced_vfx_changed`.
- Setters are no-op guards (no signal when unchanged) and persist on change. UI exposes toggles only; volumes stay internal for a future fine-tune UI.
- `init_from_save()` at boot; `reset_to_defaults()` emits ALL 8 signals (UI re-localizes + re-syncs passively).

### 3.6 LocalizationManager
- Locales: en, es (`SUPPORTED_LANGUAGES`). `.po` files REQUIRE a `Language:` header (engine gotcha — NOTES.md). `locale_applied(language_code)` signal after each switch. Scripts use `tr("key")`; formatted strings = `tr("key") % [args]` (no format-arg overload in Godot 4 `tr()`).
- **Stale-text rule**: every screen's `_apply_locale()` re-sets ALL its text (never appends); BaseScreen auto-connects `locale_applied` → virtual `_apply_locale()`.

### 3.7 Analytics
- Queue with backpressure (`MAX_QUEUE_SIZE` 500), batch flush at 25 events or every 10s, pluggable backends via `IAnalyticsBackend` (current: console + file `user://analytics.jsonl`).
- Auto-events from EventBus: `screen_view` (on screen_changed) and `experiment_exposure` (on experiment_exposed).

### 3.8 RemoteConfig
- Stub "server": `resources/config/remote_config.json`; cache `user://remote_config_cache.json`; device id persisted before fetch. Failure → last good cache → code defaults (nothing downstream breaks).
- Schema: `{flags: {name: bool}, values: {name: any}, experiments: {name: {variants: {id: {weight, params}}}}}` plus `events`/`campaigns`/`offers` arrays for zone content and `shop_items` for the Shop (Phase F1). Events = multiplayer surface: optional `kind` (`"solo_tournament"` | `"team_tournament"` = joinable per §3.23; absent = display-only), plus `metadata.tournament_id` and `rewards: [{min_rank, max_rank, currency, amount}]` rank bands (Phase F4); campaigns = solo mechanics (`action`: `"claim"` | `"modifier"` | absent; optional `ends_in_hours`, `metadata` dict with `zone`/`progress`/`dialog` keys — see GDD §6).
- **Deadline semantics**: computed at fetch/cache-load time — `deadline = fetch_unix_time + ends_in_hours × 3600`; missing/≤0 → evergreen (stored as -1). Stored in whitebox dicts `_event_deadlines` / `_campaign_deadlines` (`id -> int`) so tests can force expiry by writing past deadlines.
- **Experiment assignment**: FNV-1a (own implementation — engine `hash()` is unsuitable; NOTES.md) of `"<device_id>:<experiment>"` mapped onto cumulative weights. Stable per device. Exposure deduped per session, emitted via EventBus.
- API: `is_enabled(flag, default=false)`, `get_value(key, default=null)`, `get_experiment(name) -> variant_id`, `get_experiment_param(name, key, default)`, `log_experiment_exposure(name)`, `get_events()`, `get_campaigns()`, `get_offers()`, `get_shop_items() -> Array[Dictionary]` (Phase F1), `is_event_active(id) -> bool`, `is_campaign_active(id) -> bool` (unknown id = inactive; evergreen = always active).
- **Dev overrides** (dev/QA seams for the DevTools panel; ALL cleared by any `_apply_config()` — a refetch or cache load resets them): `set_flag(name, bool)` writes an in-memory override into `_flags`; `set_value(key, value)` writes an in-memory override into `_values` (same lifetime as `set_flag`); `force_variant(experiment_name, variant_id)` pins a variant in whitebox `_forced_variants` and is checked FIRST by `get_experiment()` (unknown experiment/variant → warning + no-op); read APIs for the panel UI: `get_flags() -> Dictionary` (copy), `get_experiment_names() -> Array[String]`, `get_experiment_variant_ids(name) -> Array[String]`.

### 3.9 AudioManager
- Buses: Master / Music / SFX / UI (`default_bus_layout.tres`). BGM tracks "menu"/"game" with crossfade; `duck_music(ratio, fade)`/`unduck_music(fade)` on the Music bus while gameplay runs. SFX: click/success/fail through a 4-slot round-robin pool + dedicated UI-bus click player. Reacts to `visibility_changed` and settings enabled-signals (disabling music stops BGM remembering `_bgm_resume_track`; re-enabling resumes).
- Known engine constraints implemented around: zero-duration tweens never fire callbacks (explicit instant paths), bound-callable `tween_method` is broken in 4.7 (plain one-arg tween targets only) — see NOTES.md.

### 3.10 AdManager
- Banner state machine `idle → loading → loaded | error`, signal `banner_state_changed(state, creative)`. 3 mock creatives `{id, title, body, color_hex}` rotating every `banner_refresh_sec`; `_generation` counter cancels in-flight loads on stop(); gated by `banner_ads_enabled`. Tracks `ad_impression`. Test hooks: `set_load_delay/set_failure_rate`.
- Dev/QA seam: `debug_fail_next_load()` — one-shot flag consumed at the failure decision of the next NON-cancelled load (the `set_failure_rate` hook cannot do this: `_failure_rate` is read after the async load await). A cancelled in-flight load leaves the flag armed for the following load.
- **Rewarded-video seam (Phase F2)**: `watch_rewarded(on_result: Callable(success: bool))` — mock completes successfully after a short simulated delay; `debug_fail_next_rewarded()` one-shot failure flag (same pattern as the banner's). Consumers: streak recovery, piggy redemption, daily-gift extra redemptions, Gift Pile saves/extra runs. DevTools Ads section gains "force-fail next rewarded" + last result row.
- **Live AdMob backend (H9/H10)**: on mobile exports with remote flag `admob_enabled` true AND non-empty unit IDs (`admob_banner_unit_id` / `admob_rewarded_unit_id`), `_refresh()` delegates the banner load to `AdMobBackend.load_banner()` (raced against `BANNER_LOAD_TIMEOUT_SEC` = 15s so a silent SDK degrades to the error state) and `watch_rewarded()` delegates to `AdMobBackend.watch_rewarded()`. A successful live banner emits `LIVE_CREATIVE` (`{id: "admob_live", native: true}`) — BannerAdSlot renders that as an empty slot because the OS draws the native banner over its region. Every other environment (desktop, headless, editor) stays on the built-in mock unconditionally — the platform guard is checked BEFORE the remote flag, so the hermetic gate is native-code free (§3.28). The QA seams (`debug_fail_next_*`, `set_failure_rate`, `set_load_delay`) are mock-path only; on-device QA uses AdMob's own test device IDs / Ad Inspector.

### 3.11 ScreenManager + ScreenShell
- **ScreenManager** (autoload, no class_name): `attach(host)` mounts the single ScreenShell full-rect and shows HOME. Screens lazily created per id, cached in a Dictionary and REUSED — swap = `remove_child` WITHOUT free. `screen_changed` emitted AFTER the content swap. Factory arms all 9 ids (`home`, `profile`, `social`, `special`, `settings`, `game`, `results`, `shop` (Phase F1), `gift_pile` (Phase F3)) + warning fallback. `ScreenIds.is_fullscreen` = GAME, RESULTS, GIFT_PILE. `shop` is NOT in the bottom NAV_ORDER — reachable only via the PlayerInfoHeader coins tap (emits `navigation_requested(&"shop")`).
- **ScreenShell** (scripts/ui/screen_shell.gd): chrome rects (fractional, full-rect parent): header y 0–0.16, content y 0.16–0.76, nav y 0.76–0.91, left zone x 0–0.18 / right zone x 0.82–1.0 at y 0.22–0.62 (Home only), banner y 0.91–1.0. Fullscreen screens (GAME/RESULTS via `ScreenIds.is_fullscreen`) get full-rect content and all chrome hidden.
- **Zone widgets** (max 6 per side): equal-height slot + centered 56px icon + 20px status banner across the icon's bottom edge (overlap 8px, ±35% width for localized strings). Icon routing: remote-config `icon` key `"gift"`/`"bank"` → animated `OfferSpriteWidget` (sprite-art offers), anything else → code-drawn `ProtoIcon`.
- **Zone placement**: left zone = events + campaigns whose `metadata.zone != "right"`; right zone = offers + campaigns whose `metadata.zone == "right"`. The `events_zone_enabled`/`offers_zone_enabled` flags gate the ZONES (not individual content).
- **Event/campaign widget lifecycle** (shell-owned): strip priority claim button > progress "N/M" (`metadata.progress`) > countdown ("Ends in H:MM", refreshed every second) > none. A widget is REMOVED live when its deadline passes (checked on the 1s tick) or is claimed, and filtered at rebuild via `RemoteConfig.is_event_active`/`is_campaign_active`. When `metadata.dialog` is present the slot becomes input-active (`MOUSE_FILTER_STOP`) and a press opens `UIManager.show_text_dialog(title, body)`.
- **Campaign claim** (shell-owned): once per id — grants `reward_currency`/`reward_amount`, stamps `campaign_claims[id] = now`, saves, emits `currency_changed` + `profile_updated`, removes the widget. No success toast (H2 policy: a claim is the direct effect of the tap — the dialog's opening clip is the feedback). Zero-amount configs never write claim stamps (save-state protection).
- **Offer claim state machine** (shell-owned): availability per kind — daily_gift: `last_daily_claim_day != today`; piggy_bank: bank balance > 0; other: cooldown elapsed or never claimed. Claim writes stamps ONLY when granted amount > 0, then emits `currency_changed` + `profile_updated` and plays the widget's opening animation — no success toast (H2 policy). Ticked every second (`_on_tick`).
- **Game flow signal ordering (CRITICAL)**: in GameScreen `_on_round_ended`, emit `navigation_requested(RESULTS)` FIRST (synchronously mounts ResultsScreen whose `_ready` connects to `gameplay_finished`), THEN emit `gameplay_finished(result)`. Reversed order = ResultsScreen never receives the data.

### 3.12 UIManager (core/ui_manager.gd, autoload, CanvasLayer layer 10)
- Four hosts in z-order bottom→top: DialogHost, TooltipHost, ToastHost, TutorialHost. All hosts are `MOUSE_FILTER_IGNORE` when idle (full-rect hosts on a high layer swallow ALL input otherwise — engine gotcha); interactive children opt into STOP while visible.
- **Dialogs**: one at a time (second request warns + rejects); `show_dialog(content, title, closable, size_hint = ZERO, use_art = true)` / `show_text_dialog(title, body)`. The panel is CENTERED in a full-rect CenterContainer and content-sized: a non-zero `size_hint` sets its minimum (content may grow it; clamped to 94%×88% of the viewport); text dialogs use `DialogHost.TEXT_DIALOG_SIZE` (560×640) so the jar art stays near its native aspect. `use_art = false` keeps the flat panel style for content-heavy dialogs (banner editor — the jar's fixed-width glass walls would dominate a ~1000px-tall frame on a 720px device). Jar-dialog headers/bodies use the ink label variations (`LabelTitleInk`/`LabelInk`) because the art's body is cream.
- **Toasts**: queue; slide in / linger / slide out; tap runs optional action or quick-dismisses. **Gate**: blocked while a dialog is open OR the current screen is fullscreen (unless spec sets `allowed_in_fullscreen`); blocked specs stay queued and are re-checked on `screen_changed`/dialog close. Signals `toast_shown`/`toast_dismissed(text, tapped)`. **Policy (H2)**: toasts are for secondary/unexpected outcomes ONLY (failures, level-up, gift-pile reveal rewards); a direct effect of a tap — claims, collects, purchases, profile picks, code copy — never toasts (inline feedback instead: the dialog's opening clip, row/header state, label swap).
- **Tooltips (long-press framework)**: opt-in per control — `UIManager.attach_tooltip(control, text, icon_key="")` / `detach_tooltip(control)`; programmatic `show_tooltip(anchor, text, icon_key)` / `dismiss_tooltip()` unchanged. Long-press state machine in TooltipHost (`LONG_PRESS_SEC = 0.5`, `SLOP_PX = 12`): a PRESS whose viewport position is inside an attached control's global rect starts a candidate; MOVE beyond slop or RELEASE before the deadline cancels it (first finger wins — extra presses while a candidate is live are ignored); on expiry the bubble shows above the anchor (clamped to viewport, flips below when there's no room). The host NEVER swallows input: a long-pressed button still fires on release, and dismissal of an existing tooltip is deferred (`call_deferred`) so the dismissing interaction still works. Dismissed also on navigation and on dialog open. New triggers are blocked by a gate `Callable -> bool` (UIManager wires it: false while a dialog is open or a tutorial is active) — same pattern as the toast gate. Attached entries persist across tree exits — screens are cached and reused, so a tooltip keeps working after navigating away and back; freed controls are dropped lazily (purged on the next attach, skipped at hit-test). No polling: `_process` early-returns unless a candidate is live. Overlapping attached controls: most recently attached wins. Offer/campaign widgets may declare `metadata.tooltip` (localized text) and ScreenShell attaches it at widget build time. Bubble style = the `PanelTooltip` theme variation.
- **Tutorial**: dim + highlight hole + gold border around a target Control; swallows all input except a press inside the target rect, which is forwarded to `Button.pressed`/`CheckBox.toggled` or a step's custom `on_interact`, then advances. Steps: `{"target": Control, "text": String, "on_interact": Callable?, "anywhere": bool?}` — `"anywhere": true` completes the step on ANY tap (off-target taps acknowledge without forwarding). **Input delivery**: events land on the topmost non-IGNORE control under the pointer — the full-rect STOP `_HighlightLayer` child, never the host's own `_gui_input` — so the layer forwards every event via `signal input_received(event)`. The emulated mouse twin of a touch tap (`device == InputEvent.DEVICE_ID_EMULATION`) is swallowed statelessly (no sticky per-tap flag: a mid-step overlay swap frees the focused control and its release is lost by the engine, which would stick any release-cleared flag forever). Signals: `tutorial_step_completed(index)`, `tutorial_finished`. Target leaving the tree (navigation) cancels the sequence.

### 3.13 Theme system
- `ThemeFactory` (scripts/ui/theme_factory.gd) is the single source of colors/margins; `resources/theme/game_theme.tres` is generated by `tools/build_theme.gd` (regenerate after palette changes). Palette: bg #10141f, panel #1b2233, gold #f5c542, blue #4f8cff, text #eef2fb/#9aa7c7 (+ silver/diamond/green/orange).
- Theme type variations (ASCII identifiers only — engine constraint): `LabelDim`, `LabelGold`, `LabelTitle`, `LabelTitleInk`, `LabelInk`, `ButtonPrimary`, `ButtonAccent`, `ButtonNav`, `PanelZone`, `PanelAvatar`. Consumed via the `theme_type_variation` property.

### 3.14 Gameplay contract
- **GameplayBase** (scripts/gameplay/gameplay_base.gd): self-contained Control widget; `start_round(duration_sec)`, `set_paused(bool)`, `stop()`, signal `round_ended(score: int)` emitted exactly once when the duration elapses; time accumulates only while running AND unpaused (pause freezes all derived timers). Generic HUD accessor `current_score: int` (subclasses keep it live; the screen HUD reads ONLY this — never gameplay-specific members). Virtuals: `_on_round_started()`, `_on_game_update(delta)`, `_final_score()`.
- **GameplayRegistry** (core/gameplay_registry.gd, autoload): key → GDScript registry of GameplayBase subclasses. `_ready()` registers the built-in `"tap_target"` → TapTargetGameplay; `register(key, script)` is the BRANCH HOOK — dropping in a new minigame = add its subclass + one register line (duplicate key warns and replaces). `create(key) -> GameplayBase` instantiates; unknown key → push_warning + tap-target fallback (a misconfigured stage never bricks the ladder).
- **StageDefinition** (scripts/gameplay/stage_definition.gd, Resource): data-driven stage entry — `id: int` (1-based ladder position = the `profile.stage` value), `name_key: String` (tr() key, "" → "Stage <id>"), `gameplay_key: String` (default "tap_target"), `duration_sec: float` (≤0 → remote `round_duration_sec`), `win_score: int` (≤0 → remote `win_score`). One .tres per stage under `res://resources/stages/`; **adding a stage = adding a file** (GDD §5).
- **StageCatalog** (core/stage_catalog.gd, autoload): loads every StageDefinition .tres from the stages dir sorted by `id`. API: `stage_count()`, `get_stage(id)` (clamped to ladder bounds), `effective_duration(stage_id)`, `effective_win_score(stage_id)` (the ≤0 → remote-default rule lives HERE, single source). Missing/empty dir → push_warning + an in-code fallback ladder of 5 generic tap-target stages (keeps existing saves playable). `load_stages(dir)` is the test seam (tests load from a temp dir and restore the default afterwards).
- **Scoring** (static, side-effect free — single source of truth for gameplay + results + tests): `tap_score(chain) = 10 + 2×maxi(chain,0)`; `coins_for_score(score, multiplier) = score/10 × multiplier` (0 for non-positive inputs); `xp_needed_for_level(level) = 100 + 50×(level−1)` (XP loop per GDD §5).
- **GameResult** (RefCounted): `{stage_id, score, best_score, is_new_best, coins_earned, xp_earned, won, duration_sec, modifiers_applied: Array[Dictionary] {stat, multiplier, title}}` + `to_dict()` (includes `modifiers_applied`).
- **Round-end modifier order** (GameScreen `_on_round_ended`, GDD §6): `base_coins = Scoring.coins_for_score(score, experiment_mult)` → `coins_earned = base_coins × ∏(active coins modifiers)` → `xp_earned = coins_earned × ∏(active xp modifiers)`. "Active" = campaign active at round end per `RemoteConfig.is_campaign_active`; each applied modifier is recorded in `modifiers_applied` and surfaced on Results + analytics.
- Current implementation: `TapTargetGameplay` (see GDD §4).

### 3.16 Online services (identity, social, save sync) — normative contract
Design intent: GDD §8 "Social & team — online services" (+ Identity/Friends/Teams/Cross-device save sync subsections). This section is the technical contract Phase D implements against; doctrine unchanged — mocks sit behind production-shaped seams, and swapping a mock for a real backend must NOT touch UI or flow code (§9). Spec'd 2026-11-06; **IMPLEMENTED 2026-11-06** (mocks + managers + sync hooks live; gate 224/224). Two implementation deviations, both documented at the source: (1) ISocialBackend's fallible methods return `Variant`, not typed arrays/dicts — Godot 4.7 cannot return `null` from a typed-array function, and `null` IS the transport/auth-failure signal (see i_social_backend.gd header); success payloads keep the types below. (2) The GDD §8 chat "bounded local retry queue on send failure" is deferred to the real backend — MockSocialBackend cannot fail, so there is nothing to retry against today; TDD never listed it as a v1 requirement.

- **IdentityService** (core/identity_service.gd, new autoload after RemoteConfig): owns player identity.
  - `get_player_key() -> String` — 32 random bytes as 64-char lowercase hex; generated once and persisted to `user://player_identity.json` (its OWN file — survives reset-save + corrupt-save quarantine).
  - `get_player_code() -> String` — derived deterministically from the key: `<WORD>-<NNNN>` (word = a small fixed list indexed by FNV-1a(key) % size; NNNN = FNV-1a(key + ":code") % 10000, zero-padded). No server round-trip needed for display or friend-add.
  - `get_auth_headers() -> Dictionary` — **the token seam**: v1 returns `{"X-Player-Key": <key>}`; a future signed-token upgrade (JWT-lite: key exchanged once for a short-lived token, refreshed on expiry) changes ONLY this method + an internal exchange/refresh — never callers, UI or flow code.
  - Failure semantics: every backend request carries the auth headers; transport/auth failure (401, timeout, offline) → the service reports unavailable and callers fall back to local/mock state (warn once per session per service — the RemoteConfig cache-fallback pattern).

- **ISocialBackend v2+** (`class_name` interface, non-singleton — IAnalyticsBackend pattern): friends + teams + chat in ONE interface (one real service). All methods awaitable (may `await` a transport internally); callers MUST `await`. Fallible methods return `Variant` (null = transport failure — see deviation note above); success payloads keep the documented types.
  - Friends: `fetch_friends() -> Array[Dictionary]` (summary shape per GDD), `add_friend(player_code) -> {ok, error}` (error keys `friend_invalid_code` / `friend_unknown_code` / `friend_already_added` / `friend_pending_exists` / `friend_blocked`; success creates a SENT invitation), `remove_friend(player_code)` (clears pendings too), `fetch_invitations() -> Array[Dictionary] {player_code, name, direction "sent"|"received", ts}`, `respond_invitation(player_code, accept: bool) -> {ok, error}` (accept/reject a RECEIVED one; `accept=false` on a SENT one cancels it; nothing pending either way → `friend_no_pending`), `block_user(player_code)`, `unblock_user(player_code)`, `fetch_blocked() -> Array[Dictionary] {player_code, name}`
  - Teams: `search_teams(query) -> Array[Dictionary] {team_id, name, access_mode "open"|"by-request", power, members, banner_recipe}`, `join_team(team_id) -> {ok, error, team}` (OPEN teams only — by-request returns `team_by_request`), `request_join(team_id) -> {ok, error, pending: bool}` (BY-REQUEST teams; errors `team_open` / `team_request_pending` / `team_already_member`; `pending` true when a request now/already exists), `leave_team()`, `fetch_team() -> Dictionary` (the `team` domain shape + `access_mode`/`leader_code`/banner recipe; empty when off-team), `create_team(name, access_mode, banner_recipe) -> {ok, error, team}` (errors `team_invalid_name` — bad name OR bad access mode — / `team_already_on_team`; creator = leader and is auto-joined), `update_team_settings(settings: Dictionary) -> {ok, error, team}` (any of name/access_mode/banner_recipe — LEADER only, else `team_not_leader`; invalid name/access mode → `team_invalid_name`), `fetch_join_requests() -> Array[Dictionary] {player_code, name, ts}` (leader only; empty for non-leaders and off-team), `respond_join_request(player_code, approve: bool)` (leader only; one-shot — the request is removed either way, approve adds the requester to the roster)
  - Chat: `fetch_chat_history(limit: int) -> Array[Dictionary]` (`{id, sender_code, sender_name, text, ts}`), `send_chat_message(text: String) -> Dictionary {ok: bool, message: Dictionary}`
  - **MockSocialBackend** = FULL LOCAL SIMULATION of the v2 surface (D5a): a fake user directory + friendships + pending invitations (both directions) + block lists + teams with settings/join requests, all in-process state. Every flow is exercisable headless; `reset()` reseeds. The one documented simplification vs Nakama: no cross-device simultaneity (one local player per process). Constructor takes the local player code (SocialManager passes `IdentityService.get_player_code()` for the default mock; tests pass a fixed code).

- **ISaveSyncBackend**: cloud-save transport.
  - `fetch_synced_domains() -> Dictionary {domains: Dictionary<String, Dictionary>, fetched_at: int}` — each domain as `{data: Dictionary, updated_at: int}`
  - `upload_synced_domains(domains: Dictionary) -> bool`
  - **MockSaveSyncBackend** = no-op success (local-only behavior — today's default).

- **SocialManager** (core/social_manager.gd, new autoload after IdentityService): owns the ISocialBackend instance + caches; the ONLY consumer-facing surface for social data (screens never touch backends directly — same doctrine as UIManager/AdManager).
  - API: `fetch_friends()`, `add_friend(code)`, `remove_friend(code)`, `fetch_invitations()`, `respond_invitation(code, accept)`, `block_user(code)`, `unblock_user(code)`, `fetch_blocked()`, `search_teams(query)`, `join_team(team_id)` (writes the `team` domain + saves via SaveSystem — the existing join flow; clears `requested_team_id`), `request_join(team_id)` (sets `requested_team_id` on success), `leave_team()` (clears `requested_team_id`), `refresh_team()`, `create_team(name, access_mode, recipe)`, `update_team_settings(settings)` (updates the local `team` domain from the result), `fetch_join_requests()`, `respond_join_request(code, approve)`, `fetch_chat(limit)`, `send_chat(text)`.

### 3.17 Nakama backend integration (D5b) — normative contract
Design intent: GDD §8 (+ "Online & offline feature availability" and "Competitive & live-ops") and BACKEND.md (server side). The real backends for the §3.16 seams, decided 2026-11-06 (DECISIONS.md): **Nakama OSS** (pinned upstream release — NO core fork) on one VPS behind Caddy, with analytics as an IN-NAKAMA Go plugin (the original Satori partner was ruled out 2026-11-07 — cloud-only; DECISIONS.md). Client = the official `heroiclabs/nakama-godot` addon (GDScript, Godot 4.x) vendored into `addons/`. Spec'd 2026-11-06; implementation = D5b.2.

- **Mode switch (build config, NOT player config)**: Godot project settings (`project.godot` `[game]`) — `backend_base_url` (String, default `""`), `nakama_server_key` (String, default `""`) — the `satori_*` settings were removed with the Satori plan (the plugin needs no client-side config; it rides the same base URL + session). **Empty `backend_base_url` = mock mode = DEFAULT** — the gate stays 100% hermetic (no network, no probing; OnlineService reports permanently ONLINE). Non-empty (e.g. `https://api.<domain>`) = real mode. Deliberately a project setting, not a save domain: it is a deploy target, not a player preference (reset-save must never wipe it), and the URL is public info — only the server key is a secret (BACKEND.md §6).
- **Nakama client ownership**: OnlineService creates the single `Nakama.create_client(server_key, host, port, scheme)` instance in real mode and OWNS it; `NakamaSocialBackend`/`NakamaSaveSyncBackend` receive it at construction (same "manager owns its backend" shape as SocialManager). Client calls return result objects with `is_exception()` — NO GDScript exceptions are thrown (NOTES.md).
- **Auth (IdentityService v2)**: the player key IS Nakama's custom-ID credential (`accounts.custom_id`; first login auto-creates the account). Flow: boot → persisted session token unexpired ⇒ `NakamaClient.restore_session(token)` — a STATIC factory that wraps the stored JWT in a `NakamaSession` with NO server call (validity is proven by the next authenticated request, and the client's auto-refresh re-exchanges on expiry); else `client.authenticate_custom_async(key, username=player_code)` → session `{token, user_id, expiry}` → persist `{key, session_token, expires_at}` to the identity file (its own file — survives reset-save/quarantine, as today). A 401/expired session during a probe ⇒ re-exchange with the raw key (the key leaves the device only inside these exchanges). `get_auth_headers()`: real mode → `{"Authorization": "Bearer <token>"}`; mock mode unchanged (`X-Player-Key`). **Username = player code** at first auth (verified: Nakama usernames allow letters/digits/`._-`, 1–128 bytes — `OWL-1234` is valid): this makes the friend-code→user lookup a native `GetUsers(usernames=[code])`. If the username is already claimed by another account (code collision, ~1 in 160k), retry WITHOUT a username — the player still works, just isn't findable by code (warn once).
- **NakamaSocialBackend** (implements ISocialBackend v2 — mapping table):

| ISocialBackend method | Nakama call | Notes |
|---|---|---|
| `fetch_friends()` | ListFriends (accepted) + user metadata per friend | summary shape per GDD §8 from user metadata `{player_code, name, level, best_score, portrait_*}` |
| `add_friend(code)` | `GetUsers(usernames=[code])` (username = player code, see Auth above), then AddFriend | creates a PENDING invitation; error keys `friend_invalid_code` / `friend_unknown_code` / `friend_already_added` / `friend_pending_exists` |

| `search_teams(query)` | ListGroups by name | `{team_id, name, banner_color, power, members}` from group metadata + member names |

| `request_join(team_id)` / `fetch_join_requests()` / `respond_join_request(code, approve)` | NATIVE: JoinGroup on a closed group / ListGroupUsers(state=3) / AddGroupUsers or KickGroupUsers | verified in `core_group.go`: joining a CLOSED group as non-admin creates a member with state 3 ("Requested to join") + notifies owner/admins; duplicate request is idempotent. Persisted in the `team` domain as five keys (§3.4) and mirrored to server group metadata (TDD §3.17; the server stores `banner_icon_scale` as a STRING like every other banner_* value — mappers parse it back with `float()`, missing key = 1.0 for pre-H7 teams).

History: the pre-art placeholders were generated once by `tools/generate_team_banners.gd` (now marked OBSOLETE-DO-NOT-RUN — it would overwrite ids 1–36 with patterns).

- **TeamBannerView** (scripts/ui/team_banner_view.gd, class_name Control): `setup(recipe: Dictionary, fallback_color: Color = Color.BLACK)` renders BannerBase full-rect + BannerIcon centered (~40% width × `icon_scale`), each through its own ShaderMaterial instance (shared shader resource). Empty recipe → flat fallback chip from `fallback_color` (legacy `banner_color` saves / unstyled teams). Used by search rows (small), the team header (large), and the banner editor (live preview).
- **Icon scale (H7, 2026-11-09)**: `icon_scale` is a uniform multiplier over the classic 0.4×0.5 centered rect, clamped to `TeamBannerView.ICON_SCALE_MIN/MAX` (0.5–1.5 — the icon never overflows the banner at any step), and re-derived into the icon layer's four anchors on EVERY render (`_apply_icon_scale()`; uniform scaling keeps the anchor box aspect invariant, so no distortion). The editor exposes it as a bounded HSlider (`banner_icon_scale` label) that emits `recipe_changed` on move; `setup(recipe)` seeds it without emitting. - **Banner editor UI** (`TeamBannerEditor`, class_name Control): live TeamBannerView preview at in-game size (48×96, centered) on top; below it FOUR horizontal slider strips — base / base palette / icon / icon palette (no vertical scroll). Each option is a flat thumbnail button with tight 2px stylebox margins and `mouse_filter = PASS` (so press/motion gestures starting on a thumbnail reach the strip's ScrollContainer, whose drag-scroll state machine consumes emulated mouse events on touch devices — see NOTES "Godot 4.7 UI layout facts"). - **Testing**: catalog counts/shape pinned + unknown-id fallback; shader smoke (mount TeamBannerView with a full recipe, await frames, no engine errors); recipe persistence round-trip through the `team` domain; editor selection → `recipe_changed` → view update.
- **Implementation notes (2026-11-09, H3)**: the shader gained a `remap_lo`/`remap_hi` luminance window (defaults 0.35/0.85) because the sheet-split art is luminance-flat and raw quantization collapsed every palette onto indices ~11–12 ("only the right-most color" symptom — see NOTES.md "Banner LUT luminance remap"). ### 3.22 Gift Pile (Phase F3) — normative contract
- **GiftPileRun** (`core/gift_pile_run.gd`, RefCounted pure state machine, seeded for deterministic tests):
  - `new_run(height: int, weights: Dictionary, seed: int, jackpot: Dictionary = {}) -> Dictionary` — pregenerates the pile bottom-up from config weights (slot = `{kind: "coins"|"gems"|"cosmetic"|"fail", amount?, cosmetic?}`); top slot forced to the passed `jackpot` (`{kind:"gems",amount:25}` when empty). The `weights` dict also carries reward-tuning keys `coin_amount` / `gem_amount` / `cosmetic_item` (read by slot generation; kind-weight keys are not tuning).
  - `reveal(run) -> {slot, banked_coins, banked_gems, danger: bool, over: bool}` — advances one slot; rewards bank, traps set `danger`.
  - `save_run(run, method: "coins"|"rv") -> run` (clears danger, marks the save consumed), `lose_run(run)`, `cash_out(run) -> {coins, gems, cosmetics}`.
  - Every mutation returns a NEW dict (no in-place mutation — GUT pins immutability).
- **Screen** `gift_pile` (fullscreen): pile column (unrevealed = covered slots, revealed = contents), banked-total HUD, [Cash Out] (disabled while in danger), danger overlay `[Save — N coins] [Watch RV] [Give up]`, jackpot flash on top-slot reveal + auto cash-out. Persists the run to the `gift_pile` domain after EVERY mutation; entering the screen with a non-null `run` resumes it (`gift_pile_run_changed` emitted).
- **Entry flow**: widget → intro dialog (rules/top prize/save cost) → Play: checks date-keyed `runs_count` vs `gift_pile_runs_per_day`; exhausted → offer RV extra watch (cap `gift_pile_extra_watches`) → navigate to the screen.
- **Trap invariant (H4, 2026-11-09)**: a trap NEVER awards directly — `reveal()` may return `over` AND `danger` simultaneously (last-slot trap; unreachable in generated piles but legal in saved runs), and the screen resolves DANGER first: the overlay opens instead of the jackpot flash. A bank is paid out only on an explicit keep: cash-out, clean top-out, or pay-to-save — a save that clears the last slot settles immediately ("keep it" with nothing left to continue). A persisted run with `danger=true` is ALWAYS resumed on entry (never auto-settled) and counts as active in the intro dialog (Continue, not Play — Play would overwrite the pending decision).
- **Re-entry (H5, 2026-11-09)**: screens are cached forever by ScreenManager and Godot 4.7 does NOT re-fire `_ready()` on re-add, so the screen re-runs its entry load on every `EventBus.screen_changed` for its own id (first emission skipped; connection kept for the instance's life — see NOTES.md engine gotchas). Round-trip coverage: `tests/test_gift_pile_roundtrip.gd`.
- **Box-selection illusion (H6, 2026-11-09)**: when `gift_pile_boxes_per_level` > 0 (default 3), the reveal trigger is a row of N closed gift boxes instead of direct slot taps (covered pile slots become visual-only). Opening ANY box reveals the predetermined next slot — pure theater, the pile shape and state machine are unchanged. A reward opens the remaining boxes with fake "possible rewards" (random cosmetic labels from `gift_pile_fake_coin/gem/cosmetic`) and locks picks for a short beat (`BOX_REVEAL_SEC`), then a fresh closed row appears; a trap keeps the unopened boxes for the next pick after the save decision, and an all-trap pool exhaustion rebuilds the row. Value 0 = legacy direct-slot mode (no row). Box state is UI-only — it never enters the persisted run dict and is rebuilt on every entry.

### 3.23 Tournaments — solo & team (Phase F4) — normative contract
- **Client API (verified in the vendored addon v3.4.0)**: `join_tournament_async(session, tournament_id)`; `write_tournament_record_async(session, tournament_id, score: int, subscore = 0, metadata = null)`; `list_tournament_records_async(session, tournament_id, owner_ids = null, limit = 10, cursor = null, expiry = null)`; `list_tournament_records_around_owner_async(session, tournament_id, owner_id, limit = 10, cursor = null, expiry = null)`; `list_tournaments_async(session, category_start, category_end, start_time, end_time, limit = 10, cursor = null)`.

  - **Auto-entry**: on `EventBus.gameplay_finished` for a WON round while a kind-bearing event is active → ensure entry (`join_tournament_async`, idempotent server-side — verify in the API spike) + accumulate progress locally (`tournaments.entries[event_id].progress += points`) + submit the RUNNING TOTAL via `write_tournament_record_async`.   - **Progress formula**: `tournament_points_per_win + floor(score / tournament_score_divisor)` (remote values).

  - **Expiry claim**: event inactive + entry exists + not claimed → band lookup by rank (`rewards` array, first matching band) → grant currency → stamp `claimed_unix` (one-shot). Team mode: reward ÷ current team size (floor per member, remainder to the leader).

Each member's won round calls `tournament_ops team_round`, which atomically INCREMENTs that group-owned record by the member's point delta — verified row shape: owner_id = group id, username = team display name, score = sum of deltas. Members without a team are rejected (`no_team`) → no entry; widget shows the join-a-team hint.
- **Tournament dialog** (zone widget tap): top-N list (rank / player code or team name / progress), own-rank row, reward bands, [Claim] at expiry; offline = disabled state per §3.18.
- **Backend**: `tournament_ops` server function (JS, same `index.js` entrypoint as `team_ops`) — actions: `ensure` (idempotent create of a plain tournament; solo + team are both plain tournaments, team scoring rides the group-owned record above) and `team_round` (atomic INCREMENT on the caller's team's record). DevTools "Ensure tournaments (F4)" action triggers ensure for every kind-bearing event; probe steps in `tools/probe_nakama.gd` cover ensure idempotency, solo join/write/best-op/around-owner, team rounds, and the no-team guard.

### 3.26 Leaderboards — global & friends (Phase E5) — normative contract
Design intent: GDD §8 "Leaderboards" bullet. Spec'd 2026-11-08; implementation = E5. ONE board, two listing scopes; scores server-owned and submitted automatically.

- **Addon API (verified in vendored v3.4.0)**: `write_leaderboard_record_async(session, leaderboard_id, score: int, subscore = 0, metadata = null)` (score serialized as a JSON string); `list_leaderboard_records_async(session, leaderboard_id, owner_ids = null, expiry = null, limit = 10, cursor = null)` — **`owner_ids` IS the friend scope** (records filtered to those user ids); `list_leaderboard_records_around_owner_async(session, leaderboard_id, owner_id, ...)` for own rank. `ApiLeaderboardRecord {leaderboard_id, owner_id, rank: String, score: String, subscore: String, num_score: int, max_num_score: int, username, metadata, create_time, update_time}` — **rank/score are JSON strings on the wire** (same gotcha as tournament records; parse with `int()`).
- **No client-side leaderboard creation**: board id `lb_best_score` is created by server function `leaderboard_ops` action `ensure` (idempotent; same single `index.js` entrypoint pattern as `team_ops`/`tournament_ops`), triggered by DevTools "Ensure leaderboards (E5)" + a probe step.
- **LeaderboardService** (new autoload after TournamentService): the ONLY owner of leaderboard state. Mock mode = inert (never faked — GDD gating table). Real mode:
  - `submit_best(score: int)` — fire-and-forget upsert; called from the stage-clear flow ONLY when the local best improves (same hook point where XP/rewards are granted); warn-once per failure class; never blocks play.
  - `fetch_leaderboard(scope: "global"|"friends", limit = 20) -> Array[Dictionary] {rank: int, name: String, score: int, is_self: bool}` — global = plain list; friends = `owner_ids` = the friend user ids (friend rows GAIN a `user_id` field in E5 — `map_user_row` extended with it; MockSocialBackend synthesizes stable fake ids). Own row comes from the around-owner call and is merged/visible even when outside top-N.
  - `is_available() -> bool` = real mode + online (TournamentService pattern).
- **UI**: new zone widget kind `leaderboards` in remote config events (icon `crown`) → ZoneDialog `LEADERBOARDS_KIND`: Global/Friends toggle, top-N rows (rank / name / score), own-rank row pinned at the bottom; offline = disabled state per §3.18.
- **Testing**: service tests with a FakeClient (submit fires a write ONLY on improvement; fetch global + friends mapping incl. string→int rank/score parse, `is_self`, empty-friends scope); friend-row `user_id` mapper pin (real + mock shapes); dialog render tests (both scopes + offline state). **Live verification** (probe step): ensure idempotency, write a record, list global, list owner-filtered (friend scope), around-owner rank.
- **Implementation notes (2026-11-09, E5 — gate 417/417, probe 27/27 live-verified; see DECISIONS.md E5 entry)**: (1) The around-owner own row rides in `records` (the window list = first + owner + second), NOT in `owner_records` — source-verified v3.37.0 `core_leaderboard.go getLeaderboardRecordsHaystack`; the service scans the window for the self id and merges only when absent. (2) The JS `leaderboardCreate` binding returns undefined → the ensure action's `created` flag comes from a `leaderboardsGetId([id])` pre-check. (3) Nakama caches JS modules at startup (no hot reload) → editing `index.js` requires a nakama container restart before the new RPC exists. (4) **Probe-caught correction to the spec's own-row bullet**: with NON-EMPTY `owner_ids`, `list_leaderboard_records` returns the filtered rows in `owner_records` (sorted, ranks filled) while `records` stays the plain global top-N window of the same call (`LeaderboardRecordsList`) — the friends scope maps `owner_records`; reading `records` would silently render global rows.

### 3.27 Matchmaking hook (Phase E4) — normative contract
Design intent: GDD §8 "Matchmaking hook" bullet. Spec'd 2026-11-08; implementation = E4. The HOOK only: queue → matched → realtime match room proven between real clients; NO in-match gameplay rides it yet (post-E4 content work plugs into `match_found` + the bridge).

- **Addon API (verified in vendored v3.4.0)**: `NakamaSocket.add_matchmaker_async(query = "*", min_count = 2, max_count = 8, string_props = {}, numeric_props = {}, count_multiple = 0) -> MatchmakerTicket`; signal `received_matchmaker_matched(MatchmakerMatched {match_id, ticket, token, users: [MatchmakerUser], self_user})`; `remove_matchmaker_async(ticket)`; `join_matched_async(matched)` (or `create_match_async` / `join_match_async(match_id)`); signals `received_match_state(MatchData)`, `received_match_presence(MatchPresenceEvent)`; `send_match_state_async(match_id, op_code: int, data: String, presences = null)`; `NakamaMultiplayerBridge` (addons/com.heroiclabs.nakama/utils) wires Godot's high-level MultiplayerAPI onto a match.
- **MatchmakingService** (new autoload after LeaderboardService): the ONLY owner of queue/match state. Mock mode = inert (never faked). Real mode:
  - `enqueue() -> Dictionary {ok, error}` — socket `add_matchmaker_async(min_count=2, max_count=2)`, holds the ticket; emits EventBus `matchmaking_state_changed(state: String, payload: Dictionary)` with states `"idle" | "queued" | "matched" | "in_match"` (`matched` payload = opponent rows `{name, player_code}` minus self).
  - On `received_matchmaker_matched` → `join_matched_async(matched)` → state `in_match`; a `NakamaMultiplayerBridge` is attached to the socket for that match (the seam future multiplayer rounds use for RPCs).
  - `cancel()` — `remove_matchmaker_async(ticket)` → `"idle"`. One queue at a time: enqueue while queued = no-op; matchmaking is player-vs-player, NOT team-scoped in v1.
- **UI**: new zone widget kind `matchmaking` in remote config events (icon `team`) → ZoneDialog `MATCHMAKING_KIND`, state-driven: idle [Find match] / queued [Cancel] / matched (opponent name + player code) / offline disabled per §3.18.
- **Testing**: service tests with a fake-socket seam (enqueue → ticket held + state emit; matched event → join called + `matched` payload correct; cancel removes the ticket; enqueue-while-queued no-op; mock mode inert); dialog render tests for all four states. **Live verification** (probe step, two clients): both enqueue → both receive `received_matchmaker_matched` naming each other → both join → one sends a match-data op and the other receives it (bridge round-trip).
- **Implementation notes (2026-11-09, E4 — gate 430/430, probe 32/32 live-verified; see DECISIONS.md E4 entry)**: (1) **Signal-order race** — `NakamaMultiplayerBridge._init` connects `received_matchmaker_matched` for auto-join, and Godot 4.7 completes `await <plain value>` SYNCHRONOUSLY (no frame suspension), so a service handler connected AFTER the bridge can observe the join ack finish before it runs: state jumps QUEUED→IN_MATCH with empty opponents and the dialog renders an empty room. Fix: the service connects its own matched handler BEFORE constructing the bridge (dispatch order = connection order), plus ordering-tolerant guards — `_on_socket_matched` sets opponents unconditionally and promotes only if still queued; `_on_bridge_match_joined` accepts MATCHED or QUEUED. Both wire orderings land on in_match with opponents populated. (2) **One dedicated socket per session, shared with the bridge** — enqueue opens a single `appear_online=true` socket; the bridge attaches to THAT socket (join + host election); cancel/leave closes it; no second connection is ever opened. (3) Wire facts pinned by the probe: `matched.users` includes SELF; the join ack's `size` is racy for sequential joins (membership proof = the match presence event, not the ack count); matches form on a fixed 15s interval (`config.go IntervalSec`) so the step uses time-based bounds up to 40s; query stays `"*"` (v3.37.0 query language ≠ master's bluge). (4) **Probe collision retry** — the 16-word × 4-digit code space (160k) plus users persisting in the dev DB across runs makes birthday-paradox 409 username collisions occasional (surfaced as flaky `auth_restore` / `block -> unblock` failures); all fresh-user sites now route through `_auth_fresh_user` (redraw up to 5 attempts on collision), mirroring OnlineService's TDD §3.17 handling while keeping the username==code assertions intact.

### 3.28 AdMob backend (H9/H10) — normative contract

Design intent: GDD §8 monetization. ## 4. Screen implementation pattern & layout contract

- Screens subclass `BaseScreen`, override `_build_ui()` and `_apply_locale()`. BaseScreen._ready(): explicit full-rect pin → guarded `_build_ui()` (once per instance) → guarded locale connect → `_apply_locale()`.
- **Special screen contract** (scripts/screens/base_special_screen.gd): `BaseSpecialScreen extends BaseScreen` with virtuals `_build_special_content(host: Control)` and `_refresh_special_content()`. The default `SpecialScreen` extends it and renders a title + body placeholder. Per GDD §7, prototypes BRANCH the repo and rewrite `special_screen.gd`; ScreenManager's factory arm is unchanged.
- **Layout contract (GOTCHA — do not violate)**:
  1. Unanchored Control children of a plain (non-container) parent collapse to minimum size at top-left. Every screen's root MarginContainer is pinned full-rect BEFORE `add_child`; same for tab sub-pages and any control hosted in a plain Control.
  2. `set_anchors_preset()` AFTER tree entry silently locks the control to 0×0 in Godot 4.7 (back-computed negative offsets; re-pinning doesn't fix). Pin with explicit anchor/offset writes (`_pin` pattern) — that's why BaseScreen._ready() never uses the preset.
  3. Containers do NOT sort hidden subtrees — measure/navigate-then-measure in probes and tests (make ancestors visible, await frames).
  4. Autowrapped Labels need a bounded `custom_minimum_size.x` or they inflate full-rect ancestors during min-size computation.
- Full details + minimal repros: NOTES.md; probe tools: `tools/probe_layout.gd`, `tools/probe_minimal.gd`.
- **Adding a new screen end-to-end** (id → factory arm → subclass → nav entry → translations → import pass → tests): step-by-step recipe with the verified template in `documentation/HOWTO_NEW_SCREEN.md` (ROADMAP C3).
